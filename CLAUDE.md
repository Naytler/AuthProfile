# CLAUDE.md

## Проект

Frontend-приложение на React + TypeScript для Yeahub.

### Стек

- React 19
- TypeScript 6
- Vite 8
- Redux Toolkit 2 / RTK Query
- React Router 7
- React Hook Form
- CSS Modules
- oxlint
- React Compiler

## Архитектура

Проект использует Feature-Sliced Design.

Структура:

```text
src/
├── app/
│   ├── App.tsx
│   ├── routes/
│   └── store.ts
├── entities/
│   ├── profile/
│   ├── skill/
│   ├── specialization/
│   └── user/
├── features/
│   ├── auth/
│   └── profile/
├── pages/
├── widgets/
├── shared/
│   ├── api/
│   ├── config/
│   ├── lib/
│   └── ui/
└── main.tsx
```

### Правила FSD

- `app` — глобальная инициализация приложения, store, router.
- `pages` — композиция страниц.
- `widgets` — крупные самостоятельные блоки интерфейса.
- `features` — пользовательские действия и сценарии.
- `entities` — бизнес-сущности и их API/model/UI.
- `shared` — переиспользуемая инфраструктура и UI без бизнес-логики.

Правило зависимостей:

```text
app
 ↓
pages
 ↓
widgets
 ↓
features
 ↓
entities
 ↓
shared
```

Слой не должен импортировать код из слоя выше него.

Не переносить код между слоями только ради формального соответствия FSD. Сначала определить, к какой ответственности он действительно относится.

### Для этого проекта

- `features/auth` — login, register, logout, session, forgot/reset password.
- `features/profile` — действия пользователя над профилем, например редактирование.
- `entities/profile` — модель профиля и profile API.
- `entities/user` — модель пользователя.
- `entities/skill` — skills API/model.
- `entities/specialization` — specializations API/model.
- `widgets/AppShell` — основная оболочка авторизованной части.
- `widgets/AuthLayout` — layout авторизации.
- `shared/ui` — Button, Input, AuthSwitch, SocialAuth и другие универсальные компоненты.
- `shared/api` — общий RTK Query API и авторизация запросов.
- `pages` — LoginPage, RegisterPage, ProfilePage, ProfileEditPage и т.д.

## TypeScript

Использовать строгую типизацию.

- Не использовать `any`, если можно описать нормальный тип.
- Использовать `unknown` для действительно неизвестных данных и безопасно сужать тип.
- Для импортов типов использовать `import type`.
- Не оставлять неиспользуемые переменные, импорты и параметры.
- Не делать `as` без необходимости.
- Не скрывать ошибки типов через `any`, `@ts-ignore` или бессмысленные приведения.
- Если API и frontend-типы расходятся, сначала разобраться с реальной структурой ответа, затем исправлять типы/mapper.

## API и RTK Query

Общий API находится в:

```text
src/shared/api/baseApi.ts
```

Авторизованные запросы используют:

```text
src/shared/api/baseQueryWithRefresh.ts
```

API отдельных сущностей и features подключаются через:

```ts
baseApi.injectEndpoints(...)
```

Не создавать отдельный Redux store/API без необходимости.

Использовать RTK Query для серверных данных вместо ручного состояния `useEffect + fetch`, если для этого уже существует API слой.

Не дублировать запросы и не создавать второй API слой для уже существующего endpoint.

## Авторизация

Текущая схема:

- access token хранится только в памяти;
- refresh token должен храниться сервером в `httpOnly` cookie;
- refresh token нельзя читать через `document.cookie` или JS-библиотеки cookies;
- access token добавляется в `Authorization: Bearer ...`;
- при `401` выполняется `GET /auth/refresh`;
- после успешного refresh новый access token сохраняется в памяти;
- исходный запрос повторяется;
- при неудачном refresh access token очищается.

Не менять эту схему без явной причины.

Не сохранять access token или refresh token в `localStorage`/`sessionStorage`, если пользователь специально не попросил изменить архитектуру.

Не добавлять ручную работу с refresh cookie на клиенте.

## Маршрутизация

Используется `react-router-dom`.

Маршруты находятся в:

```text
src/app/routes/AppRouter.tsx
```

Авторизованные страницы находятся внутри:

```text
ProtectedRoute
  → AppShell
```

Публичные страницы используют `AuthLayout`.

Не дублировать route guards внутри каждой страницы.

## Формы

Используется React Hook Form.

Предпочтительно:

- типизировать `useForm<T>()`;
- использовать `defaultValues`;
- использовать `reset()` только когда нужно явно синхронизировать уже смонтированную форму с внешними данными; не сбрасывать форму на каждый refetch;
- не дублировать состояние каждого input через `useState`, если это уже делает React Hook Form;
- ошибки формы отображать рядом с соответствующим полем.

## UI и CSS

Используются CSS Modules.

Например:

```text
Component.tsx
Component.module.css
```

Не переносить стили в styled-components или inline styles без необходимости.

Переиспользуемые UI-компоненты размещать в `shared/ui`.

Компоненты должны быть небольшими и отвечать за одну понятную задачу.

## Работа с API-ответами

Backend может возвращать данные в разных формах.

Если ответ требует преобразования, делать это в API-слое через `transformResponse` или отдельный mapper, а не размазывать преобразование по компонентам.

Пример:

```text
API response
    ↓
transformResponse / mapper
    ↓
нормализованный frontend type
    ↓
component
```

Компоненты не должны знать о нескольких возможных форматах backend-ответа.

Не придумывать поля API.

Если поле отсутствует в TypeScript-модели, но предполагается backend-ответом, сначала проверить фактический ответ/API-контракт.

Особенно внимательно проверять вложенные структуры. Например, нельзя обращаться к `profile.profiles[0]`, если `Profile` не содержит `profiles` и фактический API-ответ этого не подтверждает.

## Что делать перед исправлением бага

1. Найти компонент, где возникает ошибка.
2. Найти тип данных этого компонента.
3. Найти API endpoint, откуда приходят данные.
4. Проверить mapper/transformResponse.
5. Проверить фактическую структуру данных.
6. Исправить причину, а не только симптом.
7. Проверить связанные места использования.
8. Не менять несвязанные части проекта.
